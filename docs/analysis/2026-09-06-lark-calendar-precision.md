## 2. 直接原因：只控制手指端点，没有控制拖动过程

[CLI 的 Swipe 参数](../../Sources/AgentSoma/AgentSoma.swift#L163)仅包括方向或起止坐标；[Runner](../../Runner/LiveSessionTests.swift#L410)统一执行：

```swift
start.press(forDuration: 0, thenDragTo: destination)
```

这不是按内容偏移量滚动的接口。它规定手指的起止位置，最终内容位置仍由控件的手势识别、滚动和吸附行为决定。

本次设备日志进一步给出了实际采用的参数。六次日期滑动及其他三次拖动都是：

```text
press for 0.0 seconds
drag with velocity of 500.00 pixels per second
hold for 0.0 seconds
```

对应[原始 XCTest 日志](/private/tmp/agentsoma-501/s9c4bd8faf1a043f383cfc4b869a35d7e/xcodebuild.log:178)。坐标单位是 AgentSoma 的屏幕点；速度单位在这里保留 XCTest 日志原文，不自行按截图倍率换算。

因此，把距离由 48 缩短到 16 并不会同时降低拖动速度。当前参数下，短距离可能不改变选中项，稍大距离则跨多项。这个现象与起拖阈值、惯性和滚轮吸附共同形成的非线性响应一致；各因素的具体贡献尚未通过 Lark 触摸采样或受控实验分离。

滚轮的可见行距约为 48 点，选中行中心约为 y=385.5。第一次 48 点拖动确实大致跨一行，但最终跨了六天，说明“手指移动一行”不能当作“选中项前进一格”的保证。

`forDuration` 控制开始移动前按住多久，并不是拖动耗时。只把它从 0 改成更大的值，不能替代显式控制移动速度和结束停留。

## 3. 观察和执行语义的边界

**这次没有原生 picker wheel 可直接定位的证据。** 时间选择器暴露的是无标签、value=null 的 `scroll_view`，日期、小时和分钟作为子文字节点出现。原始类型为 46，AgentSoma 将其映射成 scroll_view 是正确的；[同一映射表](../../Sources/AgentSomaCore/XCTestCapture.swift#L109)已经支持类型 39 的 picker_wheel，所以不能归因为适配器把 picker 类型丢掉了。

虽然看起来像系统滚轮，但不能凭外观直接套用 `adjust(toPickerWheelValue:)`。原生 picker 的值设置可以作为另一条能力路径；它是否适用于某个控件，必须由实际 AX 类型和可用值证明。Appium 的[原生滚轮选择接口](https://appium.github.io/appium-xcuitest-driver/latest/reference/execute-methods/#mobile-selectpickerwheelvalue)也明确要求 PickerWheel 类型。

**画面稳定并不等于选中目标值。** 六次日期滑动都返回 completed，其中三次选中日期完全没变。现有[帧稳定逻辑](../../Sources/AgentSomaCore/FrameStability.swift#L71)判断连续帧一致；输入前 screen guard 判断画面是否仍可用于坐标操作。两者都不负责判断“是不是 9 月 7 日”。这符合现有动作契约，不能把这些回执当作业务目标已达成。

上层实际上做了反馈观察，也发现了跳过头和不移动；问题是反馈之后只继续修改距离，缺少有效的控制变量和有界的调节策略。需要保留重新观察与引用失效规则，而不是因为某次无变化就继续使用旧引用。

## 4. 后备路径存在额外的几何理解错误

`o18` 中 `10 AM` 的 AX frame 为 `y=541.6667, height=14`。这是文字框顶边，中心约为 y=548.6667，截图中的整点线与文字中心附近对齐。agent 却把约 y=542 称为整点线，并点击 y=544，结果落入前一半小时，生成 9:30–10:00。

因此，这个误差有明确的几何解释，不必归因于坐标注入随机偏移。后续重新点击 y=569 落入 10:00 时段，但仍然只是利用默认时长。

事件主体短拖没有改变时间是事实；原 agent 随后声称它“需要更长按/更慢拖拽”，只是待验证假设。本轮既没有长按对照，也没有成功拖动结束手柄，不能把该能力记为已验证。

本次日期滑动单次 Runner 约 4.11–5.56 秒，没有以前那种单次 23 秒 Spindump 阻塞的证据。主要问题转为大量试探和失败路径放大的往返成本。继续放宽 XCTest idle timeout 不会改善滚轮最终选中值；此前的[1 秒/3 秒对照](2026-09-05-swipe-wait.md#L242)还证明统一扩大等待会增加 guard 与真实输入之间的页面变化窗口。

## 6. 建议的最小优化顺序

| 优先级 | 工作 | 为什么 | 验证要求 |
| --- | --- | --- | --- |
| P0 | 为现有拖动链路贯通移动速度、起始按住时长、结束停留时长，并回显实际采用值 | 单靠距离缺少可靠的微调能力；同一链路还需要支持事件拖拽 | 在受控滚轮上测实际触摸轨迹及最终选中项，再验证 Lark |
| P0 | 将“非默认时长且开始、结束均正确”加入端到端验收 | 排除本次依靠默认 30 分钟通过的情况 | 至少覆盖 10:00–11:00、10:15–11:05，并核对保存后的起止值 |
| P1 | 上层使用目标值反馈：读当前项、调整、稳定后读实际项，限制无进展或反向振荡次数 | 有观察但没有有效控制策略仍会反复猜测 | 每步核对选中值；未达到目标不得报告时间设置成功 |
| P1 | 对确实暴露为 picker_wheel 的控件增加按值调整路径；自定义滚轮继续走可控拖动 | 原生语义动作可减少坐标依赖，但不能冒充 Lark 已支持 | 分别测试原生与 scroll_view 型控件，明确能力边界 |
| P2 | 按需返回目标区域的几何信息，并让动作后的新观察更容易一次取得 | 减少 act → observe → 多次 inspect/读图往返，避免把文字框边缘当点击区域 | 新引用仍按真实新观察生成；比较完整流程耗时与调用数 |

P0 不需要重新设计底层输入引擎。本机 XCTest SDK 的 `XCUICoordinate.h:50` 已有带 `withVelocity` 和 `thenHoldForDuration` 的重载；Appium 的[对应接口说明](https://appium.github.io/appium-xcuitest-driver/latest/reference/execute-methods/#mobile-dragfromtowithvelocity)分别描述了三个控制参数。可以直接研究 Apple API 的同一能力，不需要为此引入 WDA。

建议先以明显低于当前 500 的速度和短暂结束停留做受控对照，再确定参数，不提前把某个“慢速”数值承诺为精准滚动方案。低速加停留是否能稳定抑制该控件的惯性，以及具体需要怎样的起拖距离，都需要实测。

这些改动应继续保持当前分工：Runner 执行受守卫约束的手势并返回设备事实；外部 agent 解释日期、时间和用户目标。不把 Lark 业务规则、任务规划或无限自动重试写进通用 Runner。

## 7. 后续验证应证明什么

- 受控 Fixture 同时具有可读选中值和真实触摸记录；覆盖单格正反向、多格调整、滚动边界及无变化情形。每种关键情形重复验证，不能只看一次截图正确。
- 手势对照保持相同起点与距离，分别改变速度和结束停留，记录 touch down / move / up、最终选中项和稳定耗时，分辨是哪一个变量改善了结果。
- 验证事件块的长按移动与结束手柄调整，明确它们是否需要不同于滚动的按住时长；不能从短拖无效直接推导触发规则。
- Lark 端到端覆盖默认 30 分钟、非默认 60 分钟、非整点的 50 分钟及跨午夜场景。开始、结束、日期都须独立核对，不能只验证时长差或标题。
- 保留旧画面拒绝、旧引用拒绝、结果未知时不重放，以及保存前后核验的回归。精准拖动参数不应削弱这些现有保证。
