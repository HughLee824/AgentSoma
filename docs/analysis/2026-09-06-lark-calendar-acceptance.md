# Lark 非默认时长日程执行分析

分析对象：[预订明日开发流程会议](thread://01a07571-a8ac-7c71-8c63-592ecd34c899?hostId=local)，用户要求在 iPhone Lark 中创建明天 14:10–15:10、讨论开发流程优化事项的日程。执行基线为 `2f11f64`，使用上一轮构建的 `d113e716-8477-4e70-a6ca-5dad2a88bc56` Runner。核对了任务记录、逐次 CLI 输出、任务内嵌截图和保留的 XCTest 日志。本轮只分析，未操作手机或修改生产代码。

**本次通过了这个具体案例的非默认时长验收。** 保存前 `o15` 和保存后 `o16` 均证明时间为 2026-09-07 14:10–15:10（GMT+8），标题为“开发流程优化事项”。结束时间经过独立调整，不能再归因为默认半小时时长。六次滚轮拖动都产生了与行数相符的变化，没有重现上一轮的不移动或跨多格乱跳。剩余问题主要集中在接入诊断、观察信息获取和调用流程效率。

## 1. 可控拖动的实际验收结果

全部六次请求都显式使用 `--velocity 100 --hold-duration 0.2`，起始按住时长为默认 0；回执 `result.motion` 和 XCTest 日志中的参数一致。它们都返回 `completed`，随后分别重新 observe 核验，没有复用失效引用。

| 观察变化 | 调整对象 | 手指位移（屏幕点） | 实际值变化 |
| --- | --- | --- | --- |
| o6 → o7 | 开始日期 | 上移 48 | 9 月 6 日 → 9 月 7 日；结束日期同步到 7 日 |
| o7 → o8 | 开始小时 | 下移 48 | 15:00 → 14:00；结束时间同步为 14:30 |
| o8 → o9 | 开始分钟 | 上移 96 | 14:00 → 14:10；结束时间同步为 14:40 |
| o11 → o12 | 结束小时 | 上移 48 | 14:40 → 15:40；开始时间保持 14:10 |
| o12 → o13 | 结束分钟 | 上移 144 | 15:40 → 15:55 |
| o13 → o14 | 结束分钟 | 上移 144 | 15:55 → 15:10；小时保持 15 |

滚轮行距由 `o6/o7` 的 frame 确认约为 48 点；分钟列每格为 5 分钟。本次 48/96/144 点分别对应 1/2/3 格，日期和小时的单格正反向均有成功样本。末尾两个 144 点动作各移动三格，不能把它们描述成“第一次滚动失败后再补救”。

与[上一轮分析](2026-09-06-lark-calendar-precision.md)相比，慢速加结束停留的组合已有 Lark 实机成功证据。不过，两项参数同时变化，没有对照实验分离速度与停留各自的贡献，也没有真实触摸轨迹或重复成功率数据。本次结果不等于已证明所有控件、距离和设备上的精准滚动。

同时暴露了时间语义的边界：调整开始时间时，Lark 在本次过程中保持默认时长、联动结束时间；调整结束分钟时，`55 → 00 → 05 → 10` 没有给小时进位。调用方应按实际控件行为分别设置各列，并核对完整日期和起止值，不能把分钟列的滚动当作对完整时间做加法。这一事实应保留到后续验收中。

## 2. 接入诊断先误判了故障层级

14:41:58 开始设备发现，直到 14:45:09 才成功，约 191 秒：

- 沙盒内三次 `agentsoma devices`、一次直接 `xcrun devicectl list devices`、一次 `agentsoma connect`，共五次出现相同的 CoreDevice 初始化超时。这些失败命令累计约 78 秒。
- USB 检查只证明能看到 iPhone；同一阶段 `ps` 和 `killall` 明确出现权限拒绝，`pgrep` 也不能获取进程列表。
- agent 仍提前宣称“问题在 macOS 的 CoreDevice 服务本身”，并在沙盒外执行了 `killall CoreDeviceService`。服务重启后再次在沙盒内发现设备，依旧超时。
- 随后首次用 `require_escalated` 执行同一 `agentsoma devices`，约 3.3 秒成功；沙盒外 connect 约 18.7 秒成功。连接后全部实际输入成功。

**执行权限是本次最有力的故障线索，但不能仅据此证明 CoreDevice 从未发生暂态问题。** 没有重启前的沙盒外对照，不能完全排除重启或时间经过的影响；同样，USB 可见和超时报错不足以提前确诊系统服务损坏。

产品接口也没有帮助调用方区分这些情况：[DeviceDiscovery.swift](/Users/hui/Somnus/Project/super-indie/AgentSoma/Sources/AgentSomaCore/DeviceDiscovery.swift:22)将 devicectl 非零退出统一包成 `coredevice_failed`，只附原始错误尾部。这会让“通信权限受限”和“服务真的不可用”进入相同的恢复路径。

优先改进应是保留原始错误并标明失败阶段、给出有条件的权限诊断提示；调用方遇到相同超时且伴随权限错误时，先做同一只读命令的权限对照，再决定是否需要系统服务恢复。不能把所有初始化超时自动改写成确定的权限错误，也不应把重启服务变成默认重试步骤。

这段过程还包含尝试不存在的 launchctl 服务入口、`log` 被 shell 解释后报参数错误，以及搜索大范围历史目录找设备 ID。这些是恢复路线发散，没有提供与成本相称的新证据。

## 3. 观察接口把信息查找变成了多轮翻页

打开 More 面板后，`o2` 的截图清楚显示 Calendar 图标；默认 AX 文本仍主要是背景消息列表和底部导航。agent 已经查看该截图，之后又依次执行五次 `inspect o2`，offset 为 0、60、80、100、120，最后再次读同一截图并用坐标 `(335, 565)` 成功进入 Calendar。`o2` 到 Calendar 的 `o3` 约 83 秒。

这里有三层问题：

1. **源采集预算。** [Runner](/Users/hui/Somnus/Project/super-indie/AgentSoma/Runner/LiveSessionTests.swift:442)按树顺序深度遍历，导出前 200 个节点。背景和空容器先占预算，靠后的面板可能缺失；`o2` 确实标记了 `source_truncated=true`。
2. **文本预算与查询方式。** [observe 输出](/Users/hui/Somnus/Project/super-indie/AgentSoma/Sources/AgentSomaCore/Observation.swift:267)最多 60 行/8 KiB；提示 `unexpanded` 后，`inspect o2` 却从原始节点 0 开始输出详细 JSON，每页最多 20 个节点。它不是“继续显示剩余紧凑文本”。`inspect o2 | rg Calendar` 只搜索这一页，不是在搜索整个缓存。
3. **调用方没有及早利用已有视觉证据。** 本次十次 inspect 全部按整棵树分页，没有一次使用已有的元素引用直接 inspect 子树。时间滚轮 `o6:e50` 等引用已在默认输出中，仍从 offset 20 翻到 40 才找到日期列几何信息。

证据边界必须明确：原记录没有 inspect `o2` 的 140–199 节点，也没有保留完整 `o2/snapshot.json`。因此不能认定 Calendar 一定在 200 节点之后，更不能认定 Lark 没有暴露 Calendar 的 AX 节点。已确定的是默认输出没有给出入口、分页检索没有完整查完，而图片已经足够定位。

最小改进顺序是先使用已有的 `inspect oN:eN`，并在视觉位置明确时采用现有受 guard 保护的坐标动作。接口上可考虑增加对**整个已缓存快照**的查询，返回匹配项的引用、frame 和必要父级；明确区分“未显示”“缓存内未找到”和“源采集不完整”。源预算不足则另行考虑按目标区域/子树重新采集，不能期待 inspect 补出没有采集的数据。单纯无限增大节点预算会增加背景信息和输出成本。

## 4. 主要耗时来自调用链，而非六次拖动本身

任务有两轮：14:41:03–14:54:26 填写草稿并询问保存；14:56:21–14:57:04 用户确认后保存并退出。以下均为这一次运行的测量，不是基准性能承诺。

| 指标 | 本次记录 |
| --- | ---: |
| 首轮开始至最终完成 | 约 16 分 1 秒 |
| 两轮执行时长合计 | 约 14 分 6 秒 |
| 两轮之间等待确认 | 约 1 分 55 秒 |
| 实际 AgentSoma 业务 CLI 调用 | 50 次（含失败的 devices/connect，不含帮助和错误可执行文件路径） |
| observe / inspect | 16 次 / 10 次 |
| 已执行设备输入 | 15 次：8 tap、6 swipe、1 type，全部 completed |
| 15 次输入的 Runner 耗时合计 | 76.827 秒 |
| 六次 swipe 的 Runner 耗时合计 | 31.592 秒；单次 4.77–5.61 秒 |
| 16 次 observe 的命令耗时合计 | 11.270 秒 |

可恢复的 79 条 CommandExecution 记录，其执行时间区间合并后约 192.7 秒；另有三个 shell 请求只留下工具层错误，未生成正常的 CommandExecution 记录。不能把其余时间精确全部归给模型：其中混合了决策、工具调度、读图、审批及其他间隙。

从第一次时间选择器观察 `o6` 到填写完毕的 `o15` 约 283 秒。六个拖动在这段时间内合计只有约 32 秒，其余还有查帮助、inspect、页面切换、观察和调用间隙。当前动作回执提供稳定截图，但没有新的 AX 引用；agent 再调用 observe 获取下一轮引用，再做决策，往返成本被每一步放大。

可考虑让调用方一次取得“动作结果 + 随后的新观察”，在宿主层串行完成并生成新引用；保留 unknown 后先观察、不重发的规则，且不声称动作帧和后续 AX 是原子快照。这可以减少模型往返，不意味着省掉结果核验。

还有一个小范围的页面路径优化：开始时间设置正确后，agent 点击 Done 返回编辑页，再点击结束时间重新进入 Time。Time 页本身已经有结束时间按钮 `o9:e38`，可作为直接切换的候选路径，但本次没有实际点击验证，不能提前保证可以省掉这轮切换。

## 5. 额外确认和长时间无进展说明

原始请求已经是“替我订一个……会议日程”，主题、日期和起止时间明确。agent 也声明不添加参会人，填写结果没有偏离这项任务，却在点击 Save 前再问了一次“确认保存吗”。执行记录中没有 Save 被自动审批拒绝、或工具返回必须再次确认的记录；这是调用方主动暂停，增加了约 115 秒的用户等待和一次人工交互。

在已有创建授权、没有新增收件人或其他范围变化的情况下，核对表单后应继续保存并核对详情。该优化属于调用方的授权理解，不应给 AgentSoma Runner 加“是否允许创建日程”的业务判断。

此外，14:44:57 的权限恢复说明之后，直到 14:54:25 询问保存，约 9 分 28 秒没有用户可读的进展说明。连接已经成功、开始时间已设置、结束时间正在调整这些关键进展均未告知用户。操作正确仍可能让用户误以为任务卡住；应在关键状态变化时给出简短更新。

## 6. 次要问题与后续优先级

- 一次 tap 把可执行文件目录写成 `arm64-apple-darwin`，返回“文件不存在”，随后改回 `arm64-apple-macosx` 成功；没有派发手机输入。这是调用路径抄写问题，可通过固定已验证的可执行文件入口减少。
- 标题输入耗时约 11.1 秒。[replace 路径](/Users/hui/Somnus/Project/super-indie/AgentSoma/Runner/LiveSessionTests.swift:357)执行 tap、Command-A、type 三个 XCTest 输入；[设备日志](/private/tmp/agentsoma-501/s696d1e79f53d4961945e1ec693ba256c/xcodebuild.log:135)显示三段输入合计约 8 秒，最终帧稳定检测另约 2.39 秒。它是输入阶段的最大单项，但只出现一次，优先级低于几十次往返。若以后精简空输入框路径，需要实时证据确认焦点和空值，不能把 `value=null` 当作可靠空文本证明。
- 本次没有 Spindump 长尾、帧稳定超时、stale_reference 或 motion 回执不一致的证据；不支持继续扩大 idle timeout，也不支持因总体执行慢而重做手势引擎。

| 优先级 | 优化方向 | 可验收结果 |
| --- | --- | --- |
| P0 | 接入失败分类和调用方恢复顺序 | 同类超时不再盲重试五次；先验证权限原因，避免未经证实便重启系统服务 |
| P0 | 直接引用查询、缓存全文检索及明确的视觉后备路径 | More 面板和滚轮定位不再通过无关的 20 节点分页反复查找；保留源缺失标记 |
| P1 | 动作后取得新观察的往返合并 | 同等结果核验下减少模型调用轮次，旧引用与 unknown 语义不退化 |
| P1 | 已授权任务继续完成、关键进展说明、固定调用入口 | 不额外询问本已授权的 Save；无长时间状态沉默和二进制路径抄写错误 |
| P2 | 输入冗余和更多滚轮边界验收 | 在不削弱目标验证的前提下减少输入耗时；测 AM/PM、跨日期及重复成功率 |

后续滚轮验收应保留本次已验证的 60 分钟、非整点案例，再覆盖其他非默认时长、跨中午/午夜、反向分钟调整和多次重复。本次分钟选项为 5 分钟一格，不能据此宣称已经支持任意分钟，例如 14:13。事件块长按和结束手柄拖动同样未在本次验证。

## 后续实施（2026-09-06）

用户授权处理接入诊断和观察查询效率后，完成了以下改动：

- CoreDevice 非零退出按原始错误区分 `coredevice_initialization_timeout`、`coredevice_access_denied` 和其他 `coredevice_failed`，附失败阶段、退出码与原始日志尾部；初始化超时提示先做有条件的只读权限对照，不自动重试或重启服务。
- `inspect oN[:eN] --query TEXT` 搜索整份已缓存快照或指定子树，再按匹配列表分页；输出引用、frame、父级引用和匹配数量。搜索使用完整属性，展示时裁剪长文本，保留源缺失与引用状态。
- 默认观察的未展开提示和调用说明引导查询或直接 inspect 已知元素，避免逐页搜索无关节点。CLI 验证宿主回显查询，旧宿主静默忽略参数时明确要求重新建立会话。
- 初始针对性测试在旧行为上复现了 17 处断言失败；完成后 `swift test` 为 81 项通过、0 失败，耗时约 4.82 秒。另有真实 CLI 配合本地模拟 IPC 的[5 项检查](/private/tmp/agentsoma-query-diagnostics-validation-20260906/cli-smoke.json)全部通过。
- 实际只读设备发现验证了新诊断：沙盒内初始化超时，授权后沙盒外同一 devices 命令成功，过程中没有重启系统服务、启动 Runner 或操作 Lark。

新 CLI 已构建。此次改动只涉及 CLI/宿主，Runner 协议保持不变，可复用 actionVersion=5 的已有签名 Runner；新会话使用当前 CLI。动作与新观察的往返合并、源采集策略调整及输入冗余优化不在此次改动中，实际 Lark 全流程耗时改善仍需新会话验证。
