# AgentSoma alignment

## Outcome and current purpose

Build an open-source device embodiment layer that gives external coding agents eyes and hands on a real iPhone. The bounded no-WebDriverAgent feasibility phase has completed within the user's revised scope. Native CoreDevice communication then passed, and the user authorized the next implementation step. The minimum Swift CLI/session host now implements connect, status, open and disconnect, with verified reuse, serialization and adjustable idle cleanup. Observation, refs and the complete action contract are the next implementation step.

The interface is recorded in [the interface draft](docs/agent-interface.md), with architecture and stack decisions in [the CLI/host discussion](docs/cli-vs-mcp.md). These separate confirmed choices from remaining parameter details and unverified runtime behavior. [The v0.1 implementation plan](docs/v0.1-plan.md) records the proposed sequence and acceptance checks.

## Acceptance boundary

### Accepted examples

- A developer asks Codex or Claude Code to operate the current iOS project on one connected physical iPhone. AgentSoma returns device observations and executes the agent's device commands; the external agent owns the workflow and any assessment or presentation of its outcome.
- Later, the same device primitives let an external agent complete a natural-language task in an arbitrary installed app.

### Rejected examples

- AgentSoma embeds the model, interprets the user's natural-language goal, or owns task planning.
- AgentSoma generates test reports or manages task-level result history and retention as a product feature.
- Version 0.1 must generate a deterministic test script that can later run without an LLM.

## Invariants and non-goals

- Codex, Claude Code, or another external agent owns intent, planning, recovery decisions, and the final test judgment.
- AgentSoma owns device observation, device actions, and their immediate results: screenshots, UI structure/state, and execution outcomes or errors. The caller decides how to use or retain these outputs.
- The primary v0.1 workflow is real-device testing during iOS development.
- General automation of installed apps is a second acceptance story over the same core.
- Complete independence from WebDriverAgent is the preferred technical outcome and must be tested early.
- Use a self-authored thin Swift/XCTest Runner as the initial device backend, while preserving the option to replace it when native device capabilities suffice. Native CoreDevice-to-Runner communication has passed the bounded single-device probe; product lifecycle and recovery guarantees remain implementation work.
- Keep any Runner as thin as practical and preserve the possibility of removing it; reducing host-process count must not shift growing product responsibilities into the Runner.
- Android, device farms, a test DSL, a standalone deterministic runner, and CI integration are not current commitments.

- Actual device results on 2026-09-04: DVT screenshot succeeded at 1170×2532; AccessibilityAudit enumerated 24 Calculator elements and returned labels/identifiers; Calculator termination and relaunch were verified through process disappearance, a new PID, and a screenshot. See [the spike report](spikes/ios-direct/README.md).

- An AX hierarchy-attribute query returned one typed node with role, description, ignored state, and element identity. It did not establish a complete hierarchy or element bounds. Capability/attribute advertisement must not be treated as proof of working semantics.
- The native tunnel lost its old route once; releasing and reopening the assertion yielded a new RSD address and restored screenshot/AX reads. Automatic reconnect and a complete repeated action flow remain unverified.
- pymobiledevice3 documents independent DDI download/mounting and tunnel setup without an Xcode installation; Xcode 26 is therefore not an assumed prerequisite for the protocol spike: <https://doronz88.github.io/pymobiledevice3/guides/troubleshooting/> and <https://doronz88.github.io/pymobiledevice3/guides/ios17-tunnels/>.
- pymobiledevice3 documentation groups CoreDevice facilities under iOS 17+, but this is not a verified minimum OS for touch injection. Upstream go-ios tests of the same media-stream-gated HID route report an iOS 27 requirement on iOS 26.3/26.5, including with a newer DDI: <https://github.com/danielpaulus/go-ios/pull/843> and <https://github.com/danielpaulus/go-ios/pull/835>. One contributor reports raw input working on earlier versions without publishing that implementation; compatibility is not settled. Our iOS 26.6 device was not tested with a replacement DDI.
- Current pymobiledevice3 source exposes host-side touchscreen reports and a virtual HID keyboard through `com.apple.coredevice.hid.universalhidservice`: <https://github.com/doronz88/pymobiledevice3/blob/master/pymobiledevice3/remote/core_device/hid_service.py>.
- Its published AccessibilityAudit implementation walks focusable elements by advancing inspector focus. Its convenience API omits richer raw descriptors; the local spike queries those descriptors but has not demonstrated a complete hierarchical AX snapshot: <https://github.com/doronz88/pymobiledevice3/blob/master/pymobiledevice3/services/accessibilityaudit.py>.
- DeviceKit iOS advertises accessibility-tree and device-action APIs in an XCUITest server. Those advertised capabilities were not device-validated in this spike: <https://github.com/mobile-next/devicekit-ios/blob/main/README.md>.
- A subsequent source review of DeviceKit commit `c6a61f406d0b894bfa5864fb950eb5f8f3a20b99` found WDA-related helper implementations, including Facebook-copyrighted FBConfiguration. For the authorized XCTest spike, a separate minimal Runner using only Apple XCTest APIs was created instead; DeviceKit was not built or installed.
- Xcode 16 successfully built and signed the local Runner and a purpose-built fixture app using an existing device-authorized development profile. Both apps were installed on iOS 26.6. The native Xcode launch identified a locked-device preflight condition; after the user unlocked the device, all four XCTest cases passed: visible tap, English/Chinese text entry, swipe, and cross-app Calculator operation. Captured screenshots and hierarchy text independently confirmed `2 + 3 = 5`. No Xcode upgrade or WDA implementation was used; see [the XCTest spike](spikes/ios-xctest/README.md).
- The XCTest observation probe exported 1170×2532 screenshots, hierarchy text, and 34–46 elements per snapshot with identifiers, labels, values, enabled state, and bounds in a 390×844-point portrait window. The JSON representation is a flat list capped at 100 descendants, not yet a complete structured snapshot contract.
- The first pymobiledevice3 launch reached Runner startup but failed UI testing initialization without executing cases; its cause was not captured conclusively. A retry completed the test plan with one Calculator case passing and three Fixture cases rejected by the system as `Locked` during app launch. A later run with a measured unlocked precondition passed all four core cases, as detailed below; that success does not establish the cause of the first initialization failure.
- The subsequent live-session spike passed on the same device: one self-authored Runner processed 32 host requests with an unchanged session UUID and PID, comprising 31 successful requests and one expected missing-element error. Fixture coordinate tapping, bilingual input, three observed swipes, and error-then-success continuation passed; the same session then drove Calculator through `0 → 7 → 7× → 7×8 → 56`. Every action was followed by observation, and explicit shutdown completed the native XCTest case with zero failures. See [the live-session report](spikes/ios-xctest/LIVE.md).
- Live observation uses the public XCTest snapshot API and exports a parent-indexed list capped at 200 nodes with a truncation flag, followed by a screenshot. All 15 observed snapshots had valid parent relationships and no truncation. Host round-trip observation latency was 230–315 ms (median 285 ms); successful taps 0.40–1.27 s, three swipes 1.34–2.77 s, and one bilingual text entry including focus 3.96 s. These are one-device capability samples, not performance guarantees or proof of atomic screenshot/tree capture.
- A separate native startup timing session, with the build already installed and development services available, reached its first ping in 5.93 s without a reported unlock wait, then shut down successfully. Normal per-command TCP connections were repeatedly opened and closed during the main session; physical USB reconnect and locked-device recovery have not been tested.
- The bounded follow-up stopped the Mac iproxy process 150 ms after sending a click. The client received EOF with zero response bytes. Recreating forwarding returned the same Runner PID/session UUID; re-observation showed the click had already incremented the counter, and a new click succeeded. The unknown-outcome request was not replayed. This verifies manual forwarding recovery, not physical USB reconnect, XCTest management-channel recovery, or automatic retry. See [the extension report](spikes/ios-xctest/EXTENDED.md).
- The local WKWebView exposed accessible text, field values, bounds, and button state through XCTest. Its DOM id was absent from the AX identifier and its field label matched three nodes. A small optional element-type filter uniquely targeted the text field, entered `Web hello 你好`, and observed both the field value and JavaScript echo; a typed button query and an earlier coordinate click both incremented the web counter. This covers the controlled local page, not all hybrid apps or web content.
- A Fixture-native confirmation alert exposed duplicated nested button nodes with identical identifiers and bounds. The command rejected ambiguous targeting; the caller inspected the snapshot, selected the shared center coordinate, and verified that the alert disappeared and the local status became Confirmed. This is not an OS permission-dialog test. Both follow-up native sessions ended explicitly and passed XCTest with zero failures.
- Native devicectl lock-state preflight was tested in both states: locked rejected before XCTest; unlocked allowed the pymobiledevice3 suite to complete with four core cases passed, one unrelated live-session case skipped, no failures, and no initialization errors. The host originally misclassified the extra skipped callback as a failed plan; the raw result is preserved and a separate verification records the corrected exact-case assessment and 11 local regression checks. pymobiledevice3's own lock-state action was unsupported on this service, so the successful probe still uses Xcode's devicectl for preflight and prior Xcode build/signing. It does not prove a fully Xcode-free setup or a pymobiledevice3-launched dynamic session.
- The final requested system permission example passed: Fixture requested notification authorization from an initial notDetermined state; an explicit systemAlert observation queried SpringBoard's real notification-permission Alert, including its title and both buttons. A host command tapped Don't Allow by label and button type. Fixture then read the system authorization status as denied, and a second system Alert query confirmed zero alerts. All ten requests stayed in the same Runner/session, including one expected no-alert result; explicit shutdown ended XCTest with one pass and zero failures. This tests one permission denial flow, not generic foreground discovery or every permission type. See the system-permission section of [the extension report](spikes/ios-xctest/EXTENDED.md).

- Agent integration review on 2026-09-05: official documentation and the installed `codex mcp add --help` / `claude mcp add --help` both confirm local stdio MCP support. The MCP specification supports text and image content together in a tool response and defines stdio servers as client-launched subprocesses. These establish MCP availability, not its necessity or selection; no AgentSoma MCP server has been implemented, configured, or exercised. Sources: [Codex MCP](https://learn.chatgpt.com/docs/extend/mcp), [Claude Code MCP](https://code.claude.com/docs/en/mcp#option-3-add-a-local-stdio-server), [MCP tool results](https://modelcontextprotocol.io/specification/2025-11-25/server/tools#tool-result), [MCP stdio](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports#stdio).
- Initial CoreDevice transport review on 2026-09-05: Apple documents network-based communication with USB-connected devices, and an upstream implementation resolves a CoreDevice IPv6 address through `devicectl` JSON before contacting a custom service. The read-only review supported a direction but did not itself prove our replacement path; the Runner at that point bound only IPv4 loopback. It was followed by the separately authorized test below. See [transport evidence and sources](docs/cli-vs-mcp.md#coredevice-直连与依赖原则).
- Native transport test on 2026-09-05 passed using the existing macOS 15.0.1 / Xcode 16.0 / iOS 26.6 environment. A self-authored Swift probe used Apple devicectl JSON to discover the current IPv6 address, Foundation Process to manage xcodebuild, and Network.framework to reach the Runner directly. The only Runner behavior change was a configurable concrete listener address; token authentication and the experimental 900-second bound remained. Seven independent client processes/connections shared one Runner UUID/PID. Two observations transferred 37-node snapshots and 1170×2532 PNGs, with a verified Count 0→1 click. A 60.38-second command gap succeeded without extra probe keepalive while xcodebuild held the XCTest session. Explicit shutdown passed XCTest (1/0/0), and subsequent host/device process checks confirmed cleanup. No iproxy, pymobiledevice3, tunneld or WDA was used. CoreDevice addresses changed between preflight and launch, so new sessions must rediscover them. See [the native report](spikes/ios-xctest/NATIVE.md). This does not establish the product 30-minute idle policy, host IPC or abnormal recovery.

- Minimum Swift CLI/session host acceptance on 2026-09-05 passed: connect returns after readiness, independent CLI processes reuse the same host/Runner, canonical device locking rejects duplicate aliases, open renews idle time, and explicit disconnect exits cleanly. A separate 8-second real-device session survived its original deadline after renewal, then expired despite health traffic; host/xcodebuild and device Runner processes were confirmed absent. Both native tests passed 1/0/0; 10 local tests cover Unix IPC, in-flight/queued work, close ordering and unknown without replay. Default configuration is 1800 seconds, not a completed 30-minute soak. ArgumentParser 1.5.0 is locked; no third-party device transport tools were introduced. Runner host-managed lifetime bypasses the old spike cap; observation/ref policy remains on the host and is next. See [host acceptance](docs/session-host.md).

## Deviation policy

- Continue and record when a discovery only changes a local probe or internal implementation detail.
- The initial bounded phone-validation work was authorized to build, sign, install and run an independent XCTest helper. After requirements discussion and native CoreDevice verification, the user explicitly authorized the next implementation step. The minimum CLI/host and its local/real-device lifecycle checks are complete; continue remaining implementation under the agreed product boundaries.
- Stop and ask when evidence changes the product boundary, requires WDA, raises the minimum supported iOS version, requires an OS/Xcode upgrade, introduces unrelated installations, or alters unrelated user data on the phone.

## Verification gates

1. Prove the selected route's actual process and dependency boundary on a physical iPhone.
2. Capture a screenshot and useful structured accessibility data without WDA.
3. Complete a visible tap, swipe, and text-entry round trip, then observe the resulting state.
4. Launch and terminate a known test app and identify the foreground app.
5. Repeat a small test flow across reconnects and collect latency and failure evidence.

Current gate status after the authorized XCTest spikes: gate 1 passed for the executed route (self-authored Apple-XCTest-only Runner; no WDA implementation); gate 2 passed at the capability level (screenshot, hierarchy, useful structured attributes and bounds; product snapshot guarantees remain open); gate 3 passed in the fixture (tap, swipe, and English/Chinese text round trips, all observed), with additional local WebView input/click evidence; gate 4 partially passed (known-app lifecycle and foreground state observed, independent foreground identity unresolved); gate 5 partially passed (native and unlocked pymobiledevice3 core suites passed, and an interrupted action session resumed after forwarding recreation, but physical reconnect and lock recovery are untested).

Live-session evidence additionally covers coordinate tapping, parent-indexed snapshots, per-command latency, error-then-success continuation, two task rounds within one Runner session, and a lost-response action that had already executed. Current architecture, host language and product policies come from the explicit shared decisions above; the historical test results do not establish that those product choices have already been implemented or verified.
